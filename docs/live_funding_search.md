# Live Funding Search — 8 November 2026

This optional feature reads actual published call/topic records from two official sources. It supplements the existing general programme suggestions. It does not assess eligibility, submit an application or store funding records in SQLite. All project descriptions and local comparison inputs remain on the laptop.

- The Horizon adapter returned **20 topic records** and a visible notice that further results were not fetched. One real record was `HORIZON-CL5-2026-11-D3-06`, “Resource assessment for deep sedimentary and basement reservoirs”, source-labelled open, opening **2026-08-04**, deadline **2026-12-01**. These dates were retrieved from the API, not generated by an AI model. Its [official topic page](https://ec.europa.eu/info/funding-tenders/opportunities/portal/screen/opportunities/topic-details/HORIZON-CL5-2026-11-D3-06) is supplied by the API.

These are dated observations, not promises that the same records remain available or open. A source-labelled open record is independently checked against its date window before the UI calls it open. All source records remain visible for inspection, including closed/unknown ones.

## Status and date rules

`FundingCall` and `CallDate` are independent frozen, versioned models. Existing project schemas, prompts and repository logic are unchanged. Raw source dates are retained. A failed source has no successful call retrieval timestamp; the UI separately labels the last completed search attempt.

- ISO date-only values carry no invented clock time or timezone.
- Zoned timestamps retain their explicit offsets. Naive timestamps and invalid dates remain unknown.
- The API's midnight timestamp values are treated conservatively as calendar dates; a midnight value is not evidence of an actual midnight submission cutoff.
- For a calendar date without a verified time/zone, the status checker permits the whole calendar day across UTC+14 through UTC-12. It cannot call a date-only opening definitely past until that uncertainty window ends, nor declare a date-only deadline passed before every possible boundary has passed. This intentionally produces unknown results around boundaries.
- An explicit official closed label establishes closed status. A definitely passed deadline also produces closed. Future opening dates produce upcoming unless the source's open label conflicts. Open requires an official open label and an unambiguous current date window. Missing/conflicting dates and invalid calendar bounds produce unknown, with a reason.
- Source-labelled open Horizon topics with multiple deadlines remain unknown until a human verifies the relevant stage. Geography is not inferred from the programme name. Conditions/objectives may be shortened plain-text excerpts; that limitation is stated.
- Snapshots older than six hours, or with implausible future retrieval timestamps, become unknown without an automatic network refresh. This is a display-safety limit, not a freshness guarantee during the six-hour interval.

## Failure handling and privacy

Both adapters use fixed official hosts/paths, normal certificate verification, ten-second socket timeouts, bounded reads and no redirects or retries. Aurora limits transferred and decoded pages to 1 MB; the API limit is 2 MB per page. The API uses the trusted `certifi` bundle already supplied by the existing OpenAI/httpx dependency, with a system-trust fallback if unavailable. No packages were installed or security checks disabled. Socket timeouts do not impose a strict total wall-clock deadline for the whole search.

Unexpected MIME types, source/provenance mismatches, ignored filters, malformed records, invalid pagination and ordinary HTTP/network/protocol failures produce notices. One unavailable source does not conceal the other source's valid results. A later API page failure preserves earlier verified pages and reports partial coverage. Identical duplicates are coalesced; conflicting duplicates are omitted. A changed CSV link pattern or schema requires a future reviewed maintenance change.

Aurora's table includes broad, sometimes indicative objectives and applicant categories. It does not encode every current call-page restriction. The detailed terms prevail. The Portal excerpts also do not replace reference documents. Requirements are never classified as satisfied by a fictional project.

## Manual verification

1. Start the app normally with `streamlit run app.py`. Open a saved **fictional** idea; a generated concept is optional.
2. Expand **Find Funding Opportunities (optional)**. Choose **Search Live Funding Calls**. Check that the live-source notices and partial-result warning are visible.
3. Select a record in **Inspect a live call**. Compare its title/ID, raw and displayed dates, source label/current-status explanation, requirements, retrieval time and evidence links with the official source. For API midnight/multi-stage dates, verify the exact deadline and timezone manually in official documents.
4. Compare the local shared-topic explanation with the saved idea. It is a vocabulary overlap, not an eligibility or relevance score.
5. Rerun or select another retrieved record. No requests repeat. Switch projects or change the saved idea: results for a different idea are not displayed. After six hours, statuses become unknown until explicit search.
6. Submit the separate **Find Funding Opportunities** form to check the original six programme suggestions. Confirm generation, saved-project reopening, PDF download and consistency results remain available.
7. To test an outage manually, disconnect the network before an explicit live search. Source notices and official links/general guidance remain; existing saved project content is unchanged. Restore connectivity and explicitly search again.

## Automated checks

The normal complete pytest suite uses only fictional fixtures and mocked sources. Date/time/status, provenance, compressed-size limits, malformed responses, source isolation, pagination and Streamlit state/preservation are tested offline. Two public-source integration checks are skipped unless `HANKELUOTSI_LIVE_FUNDING=1` is explicitly set; run them separately as documented in README. They can fail when sources are unavailable or change their contract and must never become a default CI requirement.

No live-browser layout or slow-request click-concurrency test is claimed. AppTest is synchronous; its rerun tests cover completed requests. Actual user time remains for the owner to record independently.
